# Test cases

Generate the local test instances with:

```bat
python tests\generate_instances.py
```

This creates four deterministic files in `tests/generated`:

- `tiny.in`: smallest useful end-to-end case.
- `capacity.in`: checks cache capacity and competing cache latencies.
- `disconnected.in`: checks endpoints with no cache connection.
- `large.in`: 800 videos, 80 endpoints, 40 caches and 4000 requests.

Run one case from the project root with:

```bat
solver.exe < tests\generated\tiny.in > tests\generated\tiny.out
```

For the small cases, compare the genetic algorithm with an exact optimum:

```bat
python tests\optimal_solution.py tests\generated\tiny.in --solver solver.exe
python tests\optimal_solution.py tests\generated\capacity.in --solver solver.exe
python tests\optimal_solution.py tests\generated\disconnected.in --solver solver.exe
```

The exact search is deliberately limited to small instances because this
optimization problem is combinatorial. For `large.in`, compare against the
best score obtained over several runs, not an assumed exact optimum.

The solver also prints genetic algorithm progress before its solution, so the
output is useful for a runtime smoke test but is not currently a strict output
file for the Hash Code judge format.

## How the test cases are generated

The instances are generated by `tests/generate_instances.py`. Running:

```bat
python tests\generate_instances.py
```

creates the `tests/generated` directory and overwrites its four input files.
The first three cases are written manually so that each one checks a specific
behavior. The large case uses a deterministic pseudo-random generator:

```python
rng = random.Random(20260918)
```

Because the seed is fixed, the same `large.in` file is produced every time.

### `tiny.in`

This is the smallest complete case:

- 2 videos, with sizes 10 and 20;
- 1 endpoint, with a datacenter latency of 100;
- 1 cache, connected with latency 20;
- 5 requests for video 0 and 3 requests for video 1;
- cache capacity of 30.

Both videos fit exactly in the cache. The total time saved is:

```text
(100 - 20) * 5 + (100 - 20) * 3 = 640
```

There are 8 requests, so the expected score is:

```text
640 * 1000 / 8 = 80000
```

### `capacity.in`

This case contains 4 videos, 2 endpoints and 2 caches, each with capacity 50.
The endpoints have different latencies to the caches:

```text
endpoint 0 -> cache 0: 10, cache 1: 60
endpoint 1 -> cache 0: 80, cache 1: 20
```

Cache 0 is therefore more useful for endpoint 0, while cache 1 is more useful
for endpoint 1. The case checks that the solver respects cache capacity and
chooses videos according to both request counts and competing latencies.

### `disconnected.in`

The first endpoint has no cache connection at all. Its requests must therefore
be served by the datacenter and cannot produce any time saving. The second
endpoint is connected only to cache 1. This checks that a video stored in an
inaccessible cache does not incorrectly improve the score and that capacity
constraints are still respected.

### `large.in`

The large case contains:

- 800 videos;
- 80 endpoints;
- 40 caches;
- 4000 request lines;
- cache capacity of 6000.

Video sizes, endpoint latencies, cache connections and requests are generated
with the seeded random generator. Each endpoint is connected to between 8 and
25 randomly selected caches. This case is intended for runtime and quality
comparisons between several genetic algorithm runs, not for exact enumeration.

## How the exact optimum is determined

The exact reference solution is calculated by `tests/optimal_solution.py`.
It is not obtained from the genetic algorithm: the script enumerates every
valid cache configuration and keeps the one with the highest score.

### Cache configurations

For `V` videos, a cache configuration is represented by an integer bit mask.
Bit `i` is set when video `i` is stored in the cache. For example, with three
videos:

```text
000 = no video
001 = video 0
010 = video 1
111 = videos 0, 1 and 2
```

The function `feasible_masks(...)` tests all `2 ** V` masks. A mask is kept
only when the sum of the selected video sizes is no greater than the cache
capacity. The empty cache is also a valid configuration.

### Score of one complete solution

For every endpoint and every requested video, `score_solution(...)` starts
with the datacenter latency. It then examines the caches connected to that
endpoint. If a connected cache contains the video, the smallest available
latency is selected.

The saving for one video and endpoint is:

```text
(datacenter latency - best available latency) * request count
```

The final score is:

```text
1000 * total saved time / total request count
```

The division is integer division, so the result is an integer score.

### Exhaustive search

For each cache, `find_optimum(...)` tries every feasible mask. It recursively
builds all combinations of masks, one cache at a time. When every cache has a
configuration, the complete solution is scored and compared with the best
solution found so far.

If there are `N` feasible masks per cache and `C` caches, this can require up
to `N ** C` complete solutions. Since `N` can approach `2 ** V`, the number
of combinations grows very quickly. For that reason, the script rejects
instances with more than 20 videos or more than 8 caches, and the exact search
is intended only for the three small cases.

The optimum is the best score found by this exhaustive enumeration. It is
possible for several different cache layouts to have the same optimum score;
the script returns the first best layout it encounters.

For a comparison with the solver, the script parses the solver output, computes
its score using the same scoring function, and prints:

```text
optimum exact = ...
score du solveur = ...
ecart = optimum exact - score du solveur
```

An `ecart` of zero means that the genetic algorithm found an optimal solution
for that instance. For `large.in`, the exact search is intentionally not run;
the result should instead be compared with the best score obtained over
several runs.
